# AGENTS.md

agentduo is a TypeScript CLI (`src/`, published to npm as `agentduo` with bins `agentduo` and `duo`), with a VS Code extension (`extensions/vscode`) and an Electron desktop app (`apps/desktop`, design in `docs/superpowers/specs/2026-10-31-agentduo-desktop-design.md`). It is a channel between Codex CLI (planner and code reviewer) and Claude Code CLI (plan critic and implementer). The design is in `docs/superpowers/specs/2026-10-27-agentduo-channel-design.md`, which amends `2026-10-27-agentduo-npm-cli-design.md`. User docs are in `README.md`.

## Orchestrated runs

A prompt that starts with `[orchestrator-role: <role>]` comes from agentduo. Its role description and output schema are authoritative for that turn. For everything else, follow your own configuration and this file.

A prompt that starts with `[agentduo-conversation]` is a turn of the chat's three-way conversation (the user, Claude Code and Codex). It is not an orchestrated role: it has no schema, so answer in plain text, as the agent it names. When its second line is `[agentduo-discussion: <step>, round <n> of <max>]`, it is a turn of `/discuss`: the prompt says whether you answer, revise, review or synthesize the final answer (always Codex's step), and a review ends with its own `VERDICT: AGREE` or `VERDICT: REVISE` line.

## Conventions

- agentduo enforces nothing. It passes protocol flags only, plus the user's `args` and `role_args`. Unexpected changes become `warning` events, never blocks. Do not add permission flags, guards or rules to prompts; that belongs to each CLI's configuration.
- The workspace is the directory `duo` runs in. Every `Git` call runs there, so the pathspec `.` means "this workspace" and `:/` means "the whole repository".
- Node ≥ 22.12, ESM, TypeScript strict. Relative imports end in `.js`, including imports of `.ts`/`.tsx` files.
- Runtime dependencies are exactly `ink`, `react`, `commander`, `yaml` and `ajv`. Ask the user before adding another one.
- `duo` alone opens the chat (`src/chat.ts` drives runs, notes, Esc and slash commands; `src/ui/ink/ChatApp.tsx` draws it). The chat talks to its screen only through the `ChatUi` interface, so its tests use a fake one.
- Chat settings commands (`/mode`, `/claude …`, `/codex …`) mirror the CLIs' own commands and change only flags, through `src/core/settings.ts`. Each change edits `cfg.claude` / `cfg.codex` in place (the backends hold those objects) and must be idempotent, because the chat replays its changes on a resumed run, and `--global` applies a change once more over the workspace's config to tell whether that config hides it.
- Each settings change says when it applies (`SettingChange.live`): `next-call` (model, effort, permission mode, rules, add_dirs, args, role_args, bin, max_budget_usd, permission_prompts) reaches the running run, its `config.json` and a resume; `next-run` (`agents.*`, every `limits.*`) only new work, so the chat never replays it onto a saved run. Reset deletes the key (`deleteIn`); it never writes `null` to mean "inherit".
- Desktop (`apps/desktop`): a private package with its own lockfile and devDependencies only (`electron`, `electron-builder`, `@electron/fuses`, `electron-updater` (bundled into main), `playwright`); it builds from the checkout with the root toolchain, so install the root first, then `npm ci --prefix apps/desktop`. Its version follows the root's (`scripts/sync-vscode-version.mjs`). Run `npm --prefix apps/desktop run typecheck`, `test`, `build`, and `test:e2e` when you change it.
- `src/core` and `src/agents` never import from `src/ui`. Everything that reaches the screen is an `EventBus` event (`src/events.ts`), and human decisions come back through the `Decider` interface.
- Tests: `npm test` (vitest). When you change a workflow transition, add a scenario to `test/workflow.test.ts`; those scenarios drive `test/fake-agent.mjs` through real subprocesses. When a CLI's stream format changes, refresh `test/fixtures/*.jsonl` from a real run, with personal paths replaced by `/repo`.
- CI runs the tests on Windows too. A test names the user config folder with `userConfigEnv` (`test/helpers/config.ts`), never `XDG_CONFIG_HOME` alone: Windows reads `%APPDATA%`, so it would use the real user config. Compare paths built with `join`, not ones written with `/`, and use `FakeClis.path()` for a fake CLI (a `.cmd` shim on Windows).

## Gotchas

- Agent output schemas (`schemas/`) must stay OpenAI-strict: every property is listed in `required`, and `additionalProperties` is `false`. Express an optional field as a nullable type. `test/schema.test.ts` enforces this, because Codex `--output-schema` rejects anything else.
- CLI flags and stream formats were verified against codex-cli 0.164 and Claude Code 2.1.31x. After a CLI upgrade, run `duo doctor` and the parser tests.
- `git add` fails when an `:(exclude)` pathspec names an already-ignored path, so `Git.pathspec` drops ignored excludes.
- The chat and `/discuss` run in any folder, also without git. The workflow needs git but no repository: `preflightSnapshots` (`src/core/run-git.ts`, read-only, before a run or lock is created) picks the workspace's repository (native) or, in a folder with none, a bare repository of agentduo's own under the data root (`dataRoot`, never a temporary folder), and refuses the home folder (`isHomeFolder`), a data root inside the workspace, and a missing git. `Workflow.prepare` creates or opens it after the lock, before any agent and before a decision other than abort, and records it in `state.git`; a `RunGitError` leaves the run unchanged (no escalation). Every reader (`openRunGit`) follows `state.git`, never discovery again, and checks an internal repository (place derived from its id, marker) before running git in it; `prepare` also checks that its snapshots are whole (`rev-list --objects`), so a damaged one fails before a decision changes the phase. `codex exec` refuses to start outside a repository (unless Codex trusts the folder), so a conversation turn and every Codex call of an internal run pass `--skip-git-repo-check`. It is a protocol flag, not a permission: inside a repository it changes nothing.
- An internal repository's snapshots list the files themselves (`.gitignore` by path via `check-ignore --no-index`, every `.git` left out, nested repositories as plain files) and stage them with `update-index` into a copy of the index cached in its git dir: `git add` would record a nested repository as a gitlink. Its commands name `--git-dir`/`--work-tree` and drop git's local variables and `GIT_CONFIG_*`. Tests isolate the data root with `userDataEnv` (`test/helpers/config.ts`); `test/setup.ts` gives every root test file one of its own.
- Claude's stream reports each message's `usage` as the message starts, so its output tokens are far too low. The final token count comes from the result envelope's `usage`; the streamed count is only a fallback for attempts that never finished.
- Claude runs in host mode (`--input-format stream-json --permission-prompts host --permission-prompt-tool stdio`) only when the runner has a `PermissionDecider`, which the CLI passes only when someone can answer. Every other call keeps `--permission-prompts none`; without it a non-interactive run hangs on a prompt nobody answers. In host mode stdin stays open until the `result` event, and a `control_request` must always get a `control_response` (deny when in doubt).
- `/usage` reads Codex's limits from `codex app-server` (JSON-RPC lines on stdio: `initialize`, then `account/read` and `account/rateLimits/read`), because `codex exec "/status"` would send the words to the model. The app server exits as soon as its stdin closes, so `src/core/usage.ts` keeps stdin open (`holdStdin`) until both answers are in. `claude -p /usage` prints Claude Code's `/usage` without a model call, and `claude auth status` gives its plan and email as JSON; signed out, that exits with 1 and still prints the JSON.
- Codex's `--image` takes several values, so `--image a.png -` would read the prompt's `-` as one more image. Each image goes as its own `--image=<absolute path>` token.
- Claude takes images as base64 image blocks of a `--input-format stream-json` message. That input format is separate from host mode: without a `PermissionDecider` the call keeps `--permission-prompts none` and stdin closes after the message. `prompt.md` logs the text only, never the base64.
- Attached files (`src/core/attachments.ts`) are copied under the runs directory, which every snapshot excludes. A prompt lists them by path, and only `src/core/prompts.ts` writes that list.
- "Always allow" saves Claude's rule to `.claude/settings.local.json`, so `Git` excludes that file from every snapshot.
- Each pipeline role continues its own CLI session through a run (`state.sessions`, keyed by config role, so plan sign-off continues the planner's); a session passes to no other role. A continued prompt carries only what is new (files changed since the role's last turn, new notes, the work to act on), and a failed continued attempt falls back to a fresh call with the whole prompt, outside the retry budget. `--ephemeral` / `--no-session-persistence` are protocol flags: agentduo adds them, once, to every call it will not continue; in the user's args they turn continuation off. Design: `docs/superpowers/specs/2026-11-03-agentduo-context-sharing-design.md`.
- A run's budget (`limits.max_run_*`, `src/core/budget.ts`) is checked before every step and every agent attempt (`CallBudget`); a new kind of agent call or long-running step must pass through those checks. Cost is what the CLIs report: Codex reports none, so its calls count as `unpricedCalls` and its cost stays unknown, never zero. Reaching a limit escalates `budget_exhausted`, and only a `resume`/`revise` decision raises the limits reached. Design: `docs/superpowers/specs/2026-11-03-agentduo-run-budget-design.md`.
- Repository notes (`repo_notes` in the plan, critique, implementation and review schemas; `src/core/context.ts`) reach a later role only while nothing under their path changed since the turn that wrote them, and never the role that judges their author (the plan critic gets none of the planner's, the code reviewer none of the implementer's). `fake-agent.mjs` keeps sessions as the CLIs do and logs `session`, `resumed` and `lost`; a scenario's `sessions: { lost: true }` makes every resume fail.
- Changing a tab's webview options (its `localResourceRoots`) reloads the page, which would lose pasted or dropped files it is still reading. So `ConversationPanel.allow` sends `prepareReload` and changes the options only after the page answers `readyToReload`. A hidden or loading page holds no files, so its options change at once.
- The desktop renderer bundles the VS Code webview code (`extensions/vscode/webview`) but never Node: it is sandboxed and isolated, and talks to main only through the preload's `invoke`/`onEvent`. Main checks every request in `apps/desktop/src/shared/protocol.ts` (sender, shape, ids it handed out); add a method there, with its validation and a test, before using it. The renderer never names a path.
- A worker sees a config file change it did not make only through `syncConfiguration`: after any write to the user config (or a project's file), the desktop's `ProjectManager.syncConfiguration` sends it to every live worker it concerns. Settings requests call it from the `Dispatcher`; a chat command or settings menu that writes the user config (`--global`) makes its worker push `configWritten`, which does the same for the other projects. A new way of writing a config file must do the same, or other projects' chats keep their old options. A setting changed in a chat reaches the worker's other chats through `ChatOptions.changed`.
- The desktop runs the engine worker on Electron's own Node (`process.execPath` with `ELECTRON_RUN_AS_NODE=1`), so the `RunAsNode` fuse must stay on (`apps/desktop/scripts/fuses.mjs`); release builds turn `NODE_OPTIONS` and the inspector off. The worker, its `package.json` (named `agentduo`) and the schemas live outside the ASAR archive (`resources/runtime`), where `packageRoot()` finds them. Main itself runs from the archive, whose `package.json` is `agentduo-desktop`'s, so it names that folder with `setPackageRoot`.
- The desktop updates itself from published GitHub Releases (`apps/desktop/src/main/updates.ts`), which `.github/workflows/release.yml` makes from a `v*` tag: installers and feeds go to a draft, published only once all three OSes uploaded. A profile of its own (`AGENTDUO_DESKTOP_USER_DATA`, every test) never checks GitHub: it checks only `AGENTDUO_DESKTOP_UPDATE_CONFIG`'s feed and installs nothing. An ad-hoc signed Mac app cannot install an update (Squirrel.Mac wants the same Developer ID), so it only tells.
- An app opened from a launcher does not get the terminal's PATH: the desktop adds the login shell's PATH (with a timeout) and common install folders before the agents start (`apps/desktop/src/main/environment.ts`). Never interpolate user data into that shell command.
