# AGENTS.md

agentduo is a TypeScript CLI (`apps/cli`, published to npm as `agentduo` with bins `agentduo` and `duo`), with a VS Code extension (`apps/vscode`) and an Electron desktop app (`apps/desktop`, design in `docs/superpowers/specs/2026-10-31-agentduo-desktop-design.md`). It is a channel between Codex CLI (planner and code reviewer) and Claude Code CLI (plan critic and implementer). The design is in `docs/superpowers/specs/2026-10-27-agentduo-channel-design.md`, which amends `2026-10-27-agentduo-npm-cli-design.md`. User docs are in `README.md`.

## Repository map

An npm workspace. Each package has `src/` and a `test/` that mirrors it; a test lives in the package of the code it tests. Design: `docs/superpowers/specs/2026-11-05-agentduo-monorepo-layout-design.md`.

- `packages/engine` (`@agentduo/engine`): what every app runs. `src/` holds `events.ts`, `paths.ts`, `format.ts` and one folder per area: `agents/` (the CLIs, their parsers, the runner), `workflow/` (the pipeline, its state, prompts, context, budget, profiles), `quality/` (gates, acceptance, scope, findings, progress, verification), `chat/` (the chat, conversations, `/discuss`, slash commands), `clarification/`, `config/` (config files, settings, models, `init`), `git/`, `inputs/` (attachments, mentions), `system/` (doctor, environment, usage), `team/` (team mode: its config, identities, task board, worktrees, prompts and `TeamRun`). Also `schemas/`, and the shared test kit: `test/helpers`, `test/fixtures`, `test/fake-agent.mjs`.
- `packages/host` (`@agentduo/host`): what the extension and the desktop share to run the engine in a worker: `protocol.ts`, `worker.ts`, `workerClient.ts`, `runtimeSession.ts`, `workspaceSession.ts`, and `viewState.ts` (the chat's view model).
- `packages/webview` (`@agentduo/webview`): the chat's page (browser code, no Node), drawn by the extension's webviews and the desktop renderer.
- `apps/cli` (the npm package `agentduo`), `apps/vscode` (its `webview/` holds VS Code's two page entries), `apps/desktop` (outside the workspace: its own lockfile).
- `test/` at the root checks the layout itself (`boundaries.test.ts`).

## Orchestrated runs

A prompt that starts with `[orchestrator-role: <role>]` comes from agentduo. Its role description and output schema are authoritative for that turn. For everything else, follow your own configuration and this file.

A prompt that starts with `[agentduo-conversation]` is a turn of the chat's three-way conversation (the user, Claude Code and Codex). It is not an orchestrated role: it has no schema, so answer in plain text, as the agent it names. When its second line is `[agentduo-discussion: <step>, round <n> of <max>]`, it is a turn of `/discuss`: the prompt says whether you answer, revise, review or synthesize the final answer (always Codex's step), and a review ends with its own `VERDICT: AGREE` or `VERDICT: REVISE` line.

## Conventions

- agentduo enforces nothing. It passes protocol flags only, plus the user's `args` and `role_args`. Unexpected changes become `warning` events, never blocks. Do not add permission flags, guards or rules to prompts; that belongs to each CLI's configuration.
- The workspace is the directory `duo` runs in. Every `Git` call runs there, so the pathspec `.` means "this workspace" and `:/` means "the whole repository".
- Node ≥ 22.12, ESM, TypeScript strict. Relative imports end in `.js`, including imports of `.ts`/`.tsx` files.
- The published CLI's runtime dependencies (`apps/cli/package.json`) are exactly `ink`, `react`, `commander`, `yaml` and `ajv`; the workspace packages are bundled into it (devDependencies, `noExternal`). Ask the user before adding another one.
- `duo` alone opens the chat in a new conversation, `duo chat <id|latest>` a saved one (`--list` lists them) (`packages/engine/src/chat/chat.ts` drives runs, notes, Esc and slash commands; `apps/cli/src/ui/ink/ChatApp.tsx` draws it). The chat talks to its screen only through the `ChatUi` interface, so its tests use a fake one.
- Chat settings commands (`/mode`, `/claude …`, `/codex …`) mirror the CLIs' own commands and change only flags, through `packages/engine/src/config/settings.ts`. Each change edits `cfg.claude` / `cfg.codex` in place (the backends hold those objects) and must be idempotent, because the chat replays its changes on a resumed run, and `--global` applies a change once more over the workspace's config to tell whether that config hides it.
- Each settings change says when it applies (`SettingChange.live`): `next-call` (model, effort, permission mode, rules, add_dirs, args, role_args, role_models, role_efforts, bin, max_budget_usd, permission_prompts) reaches the running run, its `config.json` and a resume; `next-run` (`agents.*`, every `limits.*`) only new work, so the chat never replays it onto a saved run. Reset deletes the key (`deleteIn`); it never writes `null` to mean "inherit".
- Desktop (`apps/desktop`): a private package with its own lockfile and devDependencies only (`electron`, `electron-builder`, `@electron/fuses`, `electron-updater` (bundled into main), `playwright`); it builds from the checkout with the root toolchain, so install the root first, then `npm ci --prefix apps/desktop`. Its version follows the root's (`scripts/sync-versions.mjs`). Run `npm --prefix apps/desktop run typecheck`, `test`, `build`, and `test:e2e` when you change it.
- Packages import each other by name (`@agentduo/engine/workflow/state`: `exports` maps it to the `.ts` source; no build, no index files, so a webview bundle never pulls in Node code), never by a relative path out of their folder. The direction is engine ← host ← webview ← apps, and the CLI uses the engine only; `test/boundaries.test.ts` enforces it, and a package declares the workspace packages it imports. Test helpers are `@agentduo/engine/testing/*` and `@agentduo/host/testing/*`, for tests only. Everything that reaches the screen is an `EventBus` event (`packages/engine/src/events.ts`), and human decisions come back through the `Decider` interface.
- Tests: `npm test` (vitest, every workspace package and `test/`; the desktop runs its own). When you change a workflow transition, add a scenario to `packages/engine/test/workflow/workflow.test.ts`; those scenarios drive `packages/engine/test/fake-agent.mjs` through real subprocesses. When a CLI's stream format changes, refresh `packages/engine/test/fixtures/*.jsonl` from a real run, with personal paths replaced by `/repo`.
- CI runs the tests on Windows too. A test names the user config folder with `userConfigEnv` (`packages/engine/test/helpers/config.ts`), never `XDG_CONFIG_HOME` alone: Windows reads `%APPDATA%`, so it would use the real user config. Compare paths built with `join`, not ones written with `/`, and use `FakeClis.path()` for a fake CLI (a `.cmd` shim on Windows).

## Gotchas

- Agent output schemas (`packages/engine/schemas/`; the builds copy them beside each bundle) must stay OpenAI-strict: every property is listed in `required`, and `additionalProperties` is `false`. Express an optional field as a nullable type. `packages/engine/test/agents/schema.test.ts` enforces this, because Codex `--output-schema` rejects anything else.
- CLI flags and stream formats were verified against codex-cli 0.164 and Claude Code 2.1.31x. After a CLI upgrade, run `duo doctor` and the parser tests.
- `git add` fails when an `:(exclude)` pathspec names an already-ignored path, so `Git.pathspec` drops ignored excludes.
- The chat and `/discuss` run in any folder, also without git. The workflow needs git but no repository: `preflightSnapshots` (`packages/engine/src/git/run-git.ts`, read-only, before a run or lock is created) picks the workspace's repository (native) or, in a folder with none, a bare repository of agentduo's own under the data root (`dataRoot`, never a temporary folder), and refuses the home folder (`isHomeFolder`), a data root inside the workspace, and a missing git. `Workflow.prepare` creates or opens it after the lock, before any agent and before a decision other than abort, and records it in `state.git`; a `RunGitError` leaves the run unchanged (no escalation). Every reader (`openRunGit`) follows `state.git`, never discovery again, and checks an internal repository (place derived from its id, marker) before running git in it; `prepare` also checks that its snapshots are whole (`rev-list --objects`), so a damaged one fails before a decision changes the phase. `codex exec` refuses to start outside a repository (unless Codex trusts the folder), so a conversation turn and every Codex call of an internal run pass `--skip-git-repo-check`. It is a protocol flag, not a permission: inside a repository it changes nothing.
- An internal repository's snapshots list the files themselves (`.gitignore` by path via `check-ignore --no-index`, every `.git` left out, nested repositories as plain files) and stage them with `update-index` into a copy of the index cached in its git dir: `git add` would record a nested repository as a gitlink. Its commands name `--git-dir`/`--work-tree` and drop git's local variables and `GIT_CONFIG_*`. Tests isolate the data root with `userDataEnv` (`packages/engine/test/helpers/config.ts`); `packages/engine/test/setup.ts` gives every test file one of its own.
- Questions to the user (`packages/engine/src/clarification/clarification.ts`, no Node: the webview bundles it; `broker.ts`, `form.ts` beside it; setting `clarification.enabled`, next-call, independent of `claude.permission_prompts`). A request has an id and a `callId` of agentduo's own, options have ids, and an answer is optionIds and/or `otherText` per question id: a label or a question's text identifies nothing. Two sources: Claude's `AskUserQuestion` inside a turn (a `can_use_tool` control_request that `ClaudeParser` turns into a `question` event, never a `permission` one: no "always allow"; the reply is `updatedInput` with `answers`, keyed by the question's text, several labels joined by ", ", verified against Claude Code 2.1.318 by `packages/engine/test/fixtures/claude-question-stream.jsonl` and, opt in, `AGENTDUO_REAL_CLAUDE=1 npx vitest run packages/engine/test/agents/real-claude-question.test.ts`), and the planner's `needs_clarification` result between turns. Claude runs in host mode when someone can answer permissions or questions; the transport grants nothing, so with only questions on, every other tool request is still denied. The runner pauses both clocks while a question waits (`waits`: the time is taken off the pipeline's minutes) and settles it on result, exit and abort; Esc, a closed app or `defer` ends a Claude call and never tries to keep a tool call alive: in the chat its question is `interrupted` and the turn is not restarted; in a pipeline the question stays `pending` and is owed (`Workflow.settleQuestions` after a stopped step, `holdLeftQuestion` when a run starts, or `duo resume --answers` is applied, on a question a dead process left, so a file works without a plain resume first): the run escalates `clarification_required` for the step that asked (`resumePhase` is that step), asks it again (`held`: it can be put off, not dismissed), takes `--answers` for it, and runs the step again with the answer in its prompt, never into the old call. An answer given in an attempt of a call that then fails goes to every later attempt of that call: the runner appends it (`earlierAnswers`) to the prompt of a retry and of the fresh session after a continued one, and a session is recorded as holding an answer only because its own prompt or question had it. A conversation passes on every answer the user gave even if its turn then ended without an answer (`Exchange.unfinished`: only the question and the answers are kept; entries carry `settled` once an exchange has them, and a reopened conversation recovers the rest). The planner's schema is `packages/engine/schemas/planner.schema.json` (`result` is `anyOf` the question branch or `{ kind: plan, plan }`; `strictProblems` walks `anyOf` and `$defs`); only the plan branch is unwrapped, written as `plan.vN` and checked. A planner question does not move `planVersion`, `planningRound` or the planning convergence tracking, stops the run in `HUMAN_REVIEW` with `clarification_required` when nobody answers (`duo resume --answers <file>`, or the terminal), and a plain resume never passes it. The ledger (`state.clarifications`, `ConversationRecord.clarifications`) is saved when asked and when answered, and is the source for prompts, a reopened view and `ProgressMark` (answers received, not pending requests); sessions record which entries they have seen (ids). An answer is information: it never waives a gate, a review, the scope or a limit, and the prompts say so. The text of a question and of its options is kept as the agent wrote it (Claude's answers are keyed by it) and refused when too long, never cut. A new place that waits on the user must go through `ClarificationDecider` and the broker (idempotent, validated, per owner), never a UI-specific path.
- Claude's stream reports each message's `usage` as the message starts, so its output tokens are far too low. The final token count comes from the result envelope's `usage`; the streamed count is only a fallback for attempts that never finished.
- Claude runs in host mode (`--input-format stream-json --permission-prompts host --permission-prompt-tool stdio`) only when the runner has a `PermissionDecider`, which the CLI passes only when someone can answer. Every other call keeps `--permission-prompts none`; without it a non-interactive run hangs on a prompt nobody answers. In host mode stdin stays open until the `result` event, and a `control_request` must always get a `control_response` (deny when in doubt).
- `/usage` reads Codex's limits from `codex app-server` (JSON-RPC lines on stdio: `initialize`, then `account/read` and `account/rateLimits/read`), because `codex exec "/status"` would send the words to the model. The app server exits as soon as its stdin closes, so `packages/engine/src/system/usage.ts` keeps stdin open (`holdStdin`) until both answers are in. `claude -p /usage` prints Claude Code's `/usage` without a model call, and `claude auth status` gives its plan and email as JSON; signed out, that exits with 1 and still prints the JSON.
- Codex's `--image` takes several values, so `--image a.png -` would read the prompt's `-` as one more image. Each image goes as its own `--image=<absolute path>` token.
- Claude takes images as base64 image blocks of a `--input-format stream-json` message. That input format is separate from host mode: without a `PermissionDecider` the call keeps `--permission-prompts none` and stdin closes after the message. `prompt.md` logs the text only, never the base64.
- Attached files (`packages/engine/src/inputs/attachments.ts`) are copied under the runs directory, which every snapshot excludes. A prompt lists them by path, and only `packages/engine/src/workflow/prompts.ts` writes that list.
- `@` mentions: `packages/engine/src/inputs/mention-text.ts` is the text side (the word being typed, the insertion, the ranking) with no Node, since the webview bundles it; `packages/engine/src/inputs/mentions.ts` lists the workspace's paths (`git ls-files`, or a walk outside a repository, without the runs directory) and resolves what a message tags (`taggedPaths`: existing paths inside the workspace only). A composer asks for paths by query (`findFiles`, protocol 10) and never names a path itself. Nothing is copied: the prompt lists the tagged paths (`PromptContext.tagged`, written only by `packages/engine/src/workflow/prompts.ts`) when it is built, so no run state records them.
- "Always allow" saves Claude's rule to `.claude/settings.local.json`, so `Git` excludes that file from every snapshot.
- Each pipeline role continues its own CLI session through a run (`state.sessions`, keyed by slot: the config role, so plan sign-off continues the planner's). The one exception: the plan critic and the implementer on one CLI share the slot `plan_reviewer+implementer` (`sessionSlot`, `packages/engine/src/workflow/context.ts`), whose record also keeps the role of its last turn, each role's answers it holds and the notes it was withheld; a role with sessions off runs on its own and leaves it alone, and an older run's own-role session is continued only by that role. No other session passes between roles. A continued prompt carries only what is new (files changed since the role's last turn, new notes, the work to act on), and a failed continued attempt falls back to a fresh call with the whole prompt, outside the retry budget. `--ephemeral` / `--no-session-persistence` are protocol flags: agentduo adds them, once, to every call it will not continue; in the user's args they turn continuation off. Design: `docs/superpowers/specs/2026-11-03-agentduo-context-sharing-design.md`.
- Archiving a conversation (`archiveConversation`, `packages/engine/src/chat/conversation.ts`) is a file of its own beside the record (`archived`), never a field of `conversation.json`, so no window's save drops it; `listConversations` leaves archived ones out unless asked, and new work in one (`Chat.takeWorkspace`) restores it. `deleteConversation` removes the folder under the conversation's lock; a `Conversation` that had a record and finds it gone is `deleted`, and nothing writes it back (its `save`, the chat's work, a window's `saveView`). A new writer into a conversation's folder must check the same, or a deleted conversation comes back half.
- The workspace lock is a lease held only while work runs (`WorkspaceLease`, `packages/engine/src/workflow/lease.ts`): `Chat.takeWorkspace` takes `<runs>/.lock` and the conversation's `.lock` before an answer, a `/discuss`, a run or `/resume`, keeps them through its waits for the user, and `settled` gives them back once all it wrote is saved and its agents are gone; then it re-reads the record (`Conversation.reload`) and the config files (`beforeWork`). So `duo`, the extension and the desktop take turns, and an idle window holds nothing. A conversation write outside work (the recipient) goes under the lease or waits for the next work; a new one must too. A refused line goes back to the input (`ChatUi.refused`, `restoreDraft`), never interrupting the holder. Locks hold only the pid (older agentduo reads them); a dead holder's is taken over under a `.reclaim` guard. Waiting attachments are listed per process. Views follow other hosts by exchange id (`withRecord`, `WorkspaceSession`), and never save over a view.json that shows more. Design: `docs/superpowers/specs/2026-11-07-agentduo-window-handoff-design.md`.
- Chat and `/discuss` share one session per backend within a `Conversation`; `conversation.json` saves ids and context cursors for reopening. `/new` starts fresh. A call takes its session off the record while it runs (`takeSession`) and commits it only on success (`keepSession`); failure, interruption or explicit non-persistence flags leave none, and a discussion that ends without an answer clears every session that was in it. A failed resumed text call falls back once to the full prompt, with a warning, but not after a timeout or silence. Pipeline sessions stay role-specific.
- A run's budget (`limits.max_run_*`, `packages/engine/src/workflow/budget.ts`) is checked before every step and every agent attempt (`CallBudget`); a new kind of agent call or long-running step must pass through those checks. Cost is what the CLIs report: Codex reports none, so its calls count as `unpricedCalls` and its cost stays unknown, never zero. Reaching a limit escalates `budget_exhausted`, and only a `resume`/`revise` decision raises the limits reached. Design: `docs/superpowers/specs/2026-11-03-agentduo-run-budget-design.md`.
- A blocked implementer (`state.blocker`) runs again on `resume` only when part of its `ProgressMark` changed since the blocker: the workspace's tree, the notes it was given, the plan, the open findings or its settings (`packages/engine/src/quality/progress.ts`). Otherwise the decision escalates `no_progress` and no agent is called. A note always counts as new, and `agent_error` is retried as before. If the implementer comes to depend on a new input, add it to the mark, or a resume after a blocker will hold a run that has in fact changed. Design: `docs/superpowers/specs/2026-11-03-agentduo-no-progress-design.md`.
- Open review findings hold for the revision their review was of (`state.findingsSource`). The implementer's answers since then (`findingResponses`, `packages/engine/src/quality/findings.ts`) are claims: they are kept across attempts and rounds, blocked ones included, and only the next review replaces them (`setFindings`). A new path into IMPLEMENT, VERIFY or CODE_REVIEW must keep `findingsSource`, `findingResponses` and `gatesTree` in step: re-planning clears them. VERIFY and CODE_REVIEW first `catchUp` (re-snapshot when files changed after the last snapshot), and a review whose gates ran on an earlier tree goes back to VERIFY once per round (`reverifiedRound`). Design: `docs/superpowers/specs/2026-11-03-agentduo-review-state-design.md`.
- The acceptance contract (`packages/engine/src/quality/acceptance.ts`): the gates run once before the first plan (`state.baseline`). The plan's `baseline_failures` must cover every required gate failing then. A critique's `conflicts`, or a required gate the plan leaves out of scope while `require_tests_pass` is on, escalates `requirements_conflict` before any implementation. A review must give `origin` and `evidence` for every blocking finding, and attribute (`gate_failures`) each required gate that fails as before and lies out of scope. When only `pre_existing` blockers remain, the run escalates `preexisting_failures` instead of starting a fix round. Nothing is waived except by `resume` on those two reasons (`state.accepted`, which `revise` clears), and `DONE`'s summary names what was accepted. Design: `docs/superpowers/specs/2026-11-03-agentduo-acceptance-design.md`.
- The task's scope (`packages/engine/src/quality/scope.ts`) is a contract: the final plan's acceptance criteria (`{ id, criterion }`, `AC1`…; older plans' strings count by position) and scope. Every reviewer item is classified against it: a review finding's `origin` (`out_of_scope` is a suggestion, never fixable, never given to the implementer as work) with the `criteria` it cites, and a critique or sign-off issue's `scope`. A blocking `in_scope` finding must cite criteria the final plan has, and a refusal resting on out-of-scope items alone is retried. Only you widen the scope: a critical `out_of_scope` finding escalates `out_of_scope_critical`, a revised plan that adopts an out-of-scope issue escalates `scope_expansion`, and `resume` records either in `state.accepted.scope`. A new way of blocking on reviewer output must keep out-of-scope items out of it. Design: `docs/superpowers/specs/2026-11-03-agentduo-scope-design.md`.
- Review findings have an identity across reviews (`state.trackedFindings`, `packages/engine/src/quality/findings.ts`): matched by id (same file or close words), else by words on the same file and criteria, only when unambiguous. Only a review resolves one (by leaving it out). Each review closes a cycle (`state.cycles`); a cycle made progress when a blocking finding was resolved or stopped blocking, a required gate the task had to fix passes, or a blocking finding's file changed (`cycleProgress`, `packages/engine/src/quality/progress.ts`). Two cycles in a row without progress, or one with no file changed, escalate `review_stalled` before the next fix round; `resume` then needs something new in the `ProgressMark`, like a blocker. A new blocking finding on unchanged code needs `late_reason`. If you add a signal of progress (something that can change a review's outcome), add it to `cycleProgress`, or the run will stop a loop that is in fact moving. Design: `docs/superpowers/specs/2026-11-03-agentduo-convergence-design.md`.
- DONE rests on evidence about the final code (`packages/engine/src/quality/verification.ts`): every way to DONE goes through
  `Workflow.finalCheck`, which compares the workspace's tree and the gate configuration (`gatesConfig`) with what the
  gates ran on (`gatesTree`, the tree before they ran) and what the latest review approved (`reviewApproval`). Out of
  date, it routes back to VERIFY (same code: the approval stands) or a review, at most `FINAL_REFRESHES` times in a
  row, then escalates `verification_stale`; it never runs a gate or an agent itself. Never set `phase = "DONE"`
  anywhere else. An accepted gate counts only while the approving review still attributes it `pre_existing`, so the
  reviewer attributes accepted gates too (`gatesToAttribute`). Re-planning clears this evidence (`clearEvidence`).
  Design: `docs/superpowers/specs/2026-11-03-agentduo-final-verification-design.md`.
- Pipeline profiles (`packages/engine/src/workflow/profiles.ts`) change depth, never checks: the sign-off (`signsOff`), reviews on failing
  gates (`reviewsOnGateFailure`) and prompt notes (`profileSection`); standard's prompts and flow stay as they were.
  `state.profile` is fixed when the run starts (an older run's is standard) and only `escalateProfile` changes it,
  upward, on a deterministic signal, recorded as a step. A new way to skip work in a profile must keep every check of
  the design's list, and a new complexity signal goes through `escalateProfile`. Planning convergence follows the
  critic's issues by identity (`trackCritique`) and reuses `nextStall`: a new way to send a plan back must record its
  cycle, or the planning stall check misses it. Usage by role (`usageByRole`) comes from `addUsage`: a new agent call
  must pass its role. Design: `docs/superpowers/specs/2026-11-03-agentduo-profiles-design.md`.
- A rejected answer (not JSON, schema, or the role's `check`) is told to the next attempt with the answer itself (`rejectionNote`, `packages/engine/src/agents/runner.ts`), also in the fresh session after a rejected continued one; the same rejection twice in a row ends the call. A new check's messages must say exactly what to correct: the retry sees only them and its own answer.
- Repository notes (`repo_notes` in the plan, critique, implementation and review schemas; `packages/engine/src/workflow/context.ts`) reach a later role only while nothing under their path changed since the turn that wrote them, and never the role that judges their author (the plan critic gets none of the planner's, the code reviewer none of the implementer's). `fake-agent.mjs` keeps sessions as the CLIs do and logs `session`, `resumed` and `lost`; a scenario's `sessions: { lost: true }` makes every resume fail.
- Changing a tab's webview options (its `localResourceRoots`) reloads the page, which would lose pasted or dropped files it is still reading. So `ConversationPanel.allow` sends `prepareReload` and changes the options only after the page answers `readyToReload`. A hidden or loading page holds no files, so its options change at once.
- The desktop's styles (`apps/desktop/src/renderer/styles/`, design `docs/superpowers/specs/2026-11-12-desktop-ui-redesign.md`) are one file per area, imported by `styles.css` in cascade order; a rule reads tokens only (`tokens.css`, both themes, contrast measured), and the desktop's chat overrides sit under `body.agentduo-desktop` in `chat.css`, so VS Code's chat never changes. `test/styles.test.ts` and `test/style-contract.test.ts` refuse a raw colour outside the tokens, an undefined variable and a theme missing a token. A question to the user is `confirmDialog` (`dialog.ts`), never the browser's `confirm()`.
- The desktop renderer bundles the chat's page (`packages/webview`, with `@agentduo/host/viewState`) but never Node: it is sandboxed and isolated, and talks to main only through the preload's `invoke`/`onEvent`. Main checks every request in `apps/desktop/src/shared/protocol.ts` (sender, shape, ids it handed out); add a method there, with its validation and a test, before using it. The renderer never names a path.
- A worker sees a config file change it did not make only through `syncConfiguration`: after any write to the user config (or a project's file), the desktop's `ProjectManager.syncConfiguration` sends it to every live worker it concerns. Settings requests call it from the `Dispatcher`; a chat command or settings menu that writes the user config (`--global`) makes its worker push `configWritten`, which does the same for the other projects. A new way of writing a config file must do the same, or other projects' chats keep their old options. A setting changed in a chat reaches the worker's other chats through `ChatOptions.changed`.
- The desktop runs the engine worker on Electron's own Node (`process.execPath` with `ELECTRON_RUN_AS_NODE=1`), so the `RunAsNode` fuse must stay on (`apps/desktop/scripts/fuses.mjs`); release builds turn `NODE_OPTIONS` and the inspector off. The worker, its `package.json` (named `agentduo`) and the schemas live outside the ASAR archive (`resources/runtime`), where `packageRoot()` finds them. Main itself runs from the archive, whose `package.json` is `agentduo-desktop`'s, so it names that folder with `setPackageRoot`.
- The desktop updates itself from published GitHub Releases (`apps/desktop/src/main/updates.ts`), which `.github/workflows/release.yml` makes from a `v*` tag: installers and feeds go to a draft, published only once all three OSes uploaded. A profile of its own (`AGENTDUO_DESKTOP_USER_DATA`, every test) never checks GitHub: it checks only `AGENTDUO_DESKTOP_UPDATE_CONFIG`'s feed and installs nothing. An ad-hoc signed Mac app cannot install an update (Squirrel.Mac wants the same Developer ID), so it only tells.
- Team mode (`/team`, `duo team`; `packages/engine/src/team/`, design `docs/superpowers/specs/2026-11-12-agentduo-team-design.md`) runs beside the pipeline and changes none of it. The user hears only the PM: a `team.message` from `pm` is the only agent text the screens show, and every wait for the user (the PM's questions, the brief, plan and acceptance approvals, a conflicting apply) is a request of source `team` through the decider and the broker. Members never ask the user: the runner refuses their `AskUserQuestion` and their questions go to the techlead in their output. Each member works in its own worktree under the data root (`TeamGit`, `team/worktrees.ts`); agentduo snapshots and merges them (`merge-tree`, git 2.38+), and writes the workspace only in `apply` (a backup ref first) and `undo`, and only the tree the last whole check passed (`state.verifiedTree`). What can run is `boardJobs` (`team/board.ts`, pure); a new kind of team turn needs its job there, its strict `team_*` schema and its prompt in `team/prompts.ts`. The fake agent scripts a member with the key `<role>:<member>` (else `<role>`), and the PM's turns by occasion (`team_pm_conversation`, `team_pm_plan_review`…). Team runs live in `<runs>/teams/<id>/`, apart from pipeline runs. A team may have groups (`group` on its members): the head PM (the one PM in no group) is the only voice to the user, every group has one techlead and at most one PM of its own, and a group's work (its plan, triage, answers, merges, integration share) is its techlead's; `teamGroups` is the one source of who leads what. Files the user attaches to the request or to a message for the PM are the run's own copies (`TeamMessage.attachments`), given to every member call by `TeamRun.call` (a session that goes on gets only those it lacks, `MemberSession.files`), so a new kind of team call goes through `call`. An identity file is a whole text (the project's, else the user config's, else `team/defaults.ts`), never appended to.
- An app opened from a launcher does not get the terminal's PATH: the desktop adds the login shell's PATH (with a timeout) and common install folders before the agents start (`apps/desktop/src/main/environment.ts`). Never interpolate user data into that shell command.
